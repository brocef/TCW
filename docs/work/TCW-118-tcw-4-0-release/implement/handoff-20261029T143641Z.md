## Open question for the user: several stages sharing one Jira status

Jira mode still needs a distinct status for every enabled stage, at least
five. The work team's workflows are fixed and short. Their real flow also
spreads over several Jira projects and issue types: an intake ticket for the
request through the plan, then an epic, tasks and a QA story in a delivery
project.

The proposal waiting on the user is that several stages may name one status,
with the exact stage kept in the item's file. A move between stages that
share a status would change only the file. Options put to them:

1. Build it for 4.0.0, with one mapping per TCW project. This is the one
   recommended.
2. Build it with a mapping for each issue type.
3. Release without it; the team uses filesystem mode with the key in the
   request.

The answers drafted for the evaluator's five questions, to send once the user
decides:

- **(a) A stage on a different ticket from the item's:** no, not in 4.0.0.
  One item is one ticket.
- **(b) Parts as tasks under an epic:** partly. Parts each have their own
  ticket and stage. But without the fields, a parent in another project is
  recorded in the item's file, not linked in Jira. And the delivery project's
  task workflow has four statuses, too few for TCW's minimum of five.
- **(c) Two stages sharing one status:** yes, the proposal above.
- **(d) The smallest shape 4.0.0 drives today:** one Jira project and one
  issue type per TCW project, a status per enabled stage including one for
  discarded, and transitions into each. The intake project almost fits,
  needing only a discard status; one TCW project cannot read two intake
  projects.
- **(e) The read-and-comment mode planned for after 4.0.0:** it would read
  the request and comment, never moving tickets.

## Other open questions and concerns

- **Changes never reviewed together.** The sibling's-child lookup
  (`3edc8394`) went onto v4 without a code review: its agent's report was
  lost when the session's context was summarized. Whether the remote-URL
  matching fix (`9e03265f`) had one is not recorded either. Before the
  rebuild, review the combined diff from the last reviewed commit to v4's
  tip. Three of the changes touch `tcw/store/project.py`: the worktree
  fixes, the lookup and the URL matching. An interaction between them would
  show only in the combined diff.
- **Without the fields, no real Jira has been used.** Every test of it runs
  against the fake, and the evaluators may only do dry runs. One behavior is
  unconfirmed: whether Jira Cloud's `key IN` search finds a ticket moved to
  another Jira project when asked for its old key. The code keeps the
  `project =` clause, so a moved ticket simply drops out of the list.
  Whether to try it on a scratch Jira project is the user's call.
- **Projects sharing one Jira project must all make the same choice about
  the fields.** A project with them would adopt the request-stage items of
  one without them. Only the guide says so; `tcw validate --remote` does not
  warn. A warning is in `followups.md`.
- **Without the fields, one deleted ticket makes `tcw work list` slow.** It
  then costs one refused search plus up to 100 single reads, on every run.
  A large project could reach Jira's rate limit, and TCW does not retry.
  This is in `followups.md`, but it may matter to a team of 38 repositories
  sharing one Jira project.
- **Links between repositories without the fields** are recorded in the
  item's file only. The planning-workspace shape suggested in answer (b)
  would then show no parent links in Jira.
- **One TCW project reads one Jira project.** Two intake projects feeding
  one repository cannot be served in 4.0.0, with or without shared statuses.
- **The release keeps growing.** The gate 1 build is superseded twice over:
  by the fixes, and by optional fields. A shared-statuses change would be a
  third Jira-mode design change after the plan was written. Whether 4.0.0
  should take it, or ship and take it in 4.1, is the user's decision; they
  have said a delay is acceptable.
- **GitHub reports 2 moderate Dependabot alerts** on the default branch.
  Nobody has looked at them; check whether they touch what 4.0 ships.
