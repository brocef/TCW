# v4.0.0

TCW 4.0 is a major release. It changes where a project keeps its files, which
now sit together in a `.tcw/` folder, and how projects relate to each other:
a project names its parents, in place of the 3.x `projects:` list and
`extends`. A TCW 3.x project must be migrated with `tcw migrate` before 4.0
will work in it; [the migration guide](../migration-guide-3.X-to-4.0.0.md)
says how.

The work lifecycle and what Jira mode asks of a Jira project stay as they
were in 3.x: the same stages, the same checks at each move, and the same TCW
fields, issue type and status for each stage. The stage prompts and checks
change only where they name 4.0's commands and identifiers. Changes to the
work system are planned for TCW 5.0.

## Upgrading

- To move a project across, follow
  [the migration guide](../migration-guide-3.X-to-4.0.0.md).
- Keep any CI job or other automation that installs `tcw-cli` at
  `tcw-cli<4` until the project it works on is migrated.
- Everyone working on a project upgrades together: TCW 4.0 refuses a 3.x
  project's files except to migrate them.
- Commit your work, or back it up, before running `tcw migrate` for real,
  that is without `--dry-run`.
- From 4.0, the plugin installs the CLI of its own version
  (`tcw-cli==<the plugin's version>`), so a plugin update brings the matching
  CLI, and holding the plugin at an older version holds the CLI it installs
  at that version too. To stay on 3.x, keep the plugin at 3.0.2 by pinning it
  to the tag `v3.0.2`. Claude Code: `claude plugin marketplace remove tcw`,
  then `claude plugin marketplace add brocef/TCW#v3.0.2` and
  `claude plugin install tcw@tcw`. Codex:
  `codex plugin marketplace remove tcw`, then
  `codex plugin marketplace add brocef/TCW --ref v3.0.2` and
  `codex plugin add tcw@tcw`; Codex refreshes its marketplaces every time it
  starts, so without the pin it moves to 4.0 on its own. Pi:
  `pi remove git:github.com/brocef/TCW`, then
  `pi install git:github.com/brocef/TCW@v3.0.2`. Every move back to 3.0.2
  then needs one step of its own, because the 3.0.2 plugin installs the
  newest CLI, with no version limit, which is now 4.0. In Claude Code it does
  so at the start of a session whenever its record of the last install,
  which holds the plugin version it installed for, is missing or names a
  different version, or `tcw` is not on PATH. A plugin that had already
  moved to 4.0 left a record naming 4.0, so the first session after the
  move back installs the 4.0 CLI. In Codex and Pi, the setup skill runs the
  same install when `tcw` is missing. It leaves alone a `tcw` that is not a
  plain installed copy, such as one installed from a source folder for
  development, and does nothing when `pipx` is not installed. So once the
  first session on the 3.0.2 plugin has started (its start-up hook has
  already run), or once the setup skill has installed `tcw`, run
  `pipx install --force 'tcw-cli<4'` once. Running it before that first
  session does not last, since that session's start-up installs the newest
  CLI again. Until you run it, that first session has the 4.0 CLI under the
  3.x skills, so do nothing in a 3.x project in it until the CLI is pinned.
  After it, the record matches the plugin, and the 3.0.2 plugin leaves the
  CLI alone.
- TCW 3.x keeps a home: the branch `3.x` holds the last 3.x code. If a 3.x
  patch is ever needed, it is cut on that branch and published by pushing its
  tag.

## TCW's files move into a `.tcw/` folder

A project's configuration now lives in a `.tcw/` folder at the project's root:
`.tcw/tcw-config.yaml` for the team, and `.tcw/tcw-config.local.yaml` for your
own settings. `tcw project new` creates the folder, and inside a git repository it
keeps your personal file out of version control with a rule in
`.tcw/.gitignore`, instead of a line in the root `.gitignore`.

Paths in the configuration mean what they meant before: they are read from the
project's root, not from inside `.tcw/`. A `file: docs/lifecycle/spec.md`
binding still names `docs/lifecycle/spec.md` in your project, and a script a
binding runs still sees the project root as `TCW_CONFIG_DIR`. Running a command
from any subfolder, `.tcw/` itself included, acts on the project as before.

## Every file says which version of TCW wrote it

The first line of `.tcw/tcw-config.yaml` is now `tcw-version: 4.0.0`, the
version of TCW whose file format the file follows. TCW writes it when it creates
the file, and no ordinary edit changes it. Your personal file needs the same
line; if it is missing, TCW tells you exactly what to add.

Before reading a file, TCW checks that line, so it never misreads a file it does
not understand. A file with no version, or one from TCW 3, is refused with a
message pointing to `tcw migrate`; a file written by a newer TCW than yours is
refused with a message asking you to upgrade. `tcw validate` reports the same
problems, and also warns when an old `tcw-config.yaml` is still sitting at the
root of a project that has moved to the `.tcw/` folder.

## TCW 3 projects need converting

A project still laid out for TCW 3, with `tcw-config.yaml` at its root and no
`.tcw/` folder, is refused by every command with a message naming
`tcw migrate`, and nothing is written to it. A connected project still in the
TCW 3 layout is reported the same way and is not read. `tcw --version` and
`--help` work anywhere.

## One spelling for every setting name

Every setting name is now lowercase letters and digits joined by single
hyphens, like project IDs. A binding's `when: {not_tags: [...]}` becomes
`when: {not-tags: [...]}`; the old spelling is refused with a message saying
what to write. `tcw work lifecycle --json` prints `not-tags` too.

## Where other projects are: the manifest

`projects:` in `.tcw/tcw-config.yaml` now names connected projects by ID only:

    projects:
      parent:
        ws:
      upstream:
        lib:

Where each one is on disk goes in a manifest beside it. `.tcw/tcw-manifest.yaml`
is committed and shared; `.tcw/tcw-manifest.local.yaml` is yours alone, read
first, and kept out of version control (`tcw project new` adds it to
`.tcw/.gitignore`). An entry is a path relative to the project, or a mapping
that also gives the repository the project comes from:

    tcw-version: 4.0.0
    projects:
      ws: ..
      lib:
        path: ../lib
        repository: https://example.com/lib.git#main

A `projects:` entry that still holds a location, as in TCW 3, is refused with
the manifest entry to write instead.

## TCW finds a project even with no manifest

When no manifest places a project, TCW looks for it in the folders next to the
project that names it and in the folders enclosing it, never inside a project.
Two folders declaring the same ID are an error naming both. `TCW_PROJECT_<ID>`
still decides over everything. `tcw project list --json` now says how each
project was found.

## A project not on this machine says how to get it

A connected project that is not here, including one whose folder is empty or
holds only `.git`, is reported with where its manifest places it and, when the
entry gives a repository, the command that fetches it:
`tcw project provision <id>`. `tcw project provision --component` fetches
only the component stores a project declares.
`tcw validate` checks every entry of your manifests, and warns when your
personal manifest is tracked by version control.

## Git worktrees

A linked worktree has no personal files until you make them. When it has no
`.tcw/tcw-config.local.yaml` or `.tcw/tcw-manifest.local.yaml` of its own, the
main checkout's is used. Projects outside the repository are found from the
main checkout.

## Parents, and what each passes down

A project now names the projects it builds on under `parents:` in
`.tcw/tcw-config.yaml`, by ID and in order. A project may have several parents,
and each says what it passes down: everything (`inherit: all`, the default),
nothing (`inherit: none`), or a list drawn from `taxonomy`, `capabilities` and
`config`:

    parents:
      - core
      - id: workspace
        inherit: [config]

The parent does not have to name the child. A parent may list its children
under `children:`, in its committed file, in its personal
`.tcw/tcw-config.local.yaml`, or both; the personal list only adds, and the
user-wide file cannot list children. Every listed child must name its parent.

## The order ancestors are read in

A project's ancestors are read in one order, the load order, which ends with
the project itself. TCW works it out the way Python orders a class's bases, so
that a later parent wins over an earlier one and every project's own order of
parents is kept. When no order can keep them all, TCW uses a depth-first order
and `tcw validate` warns, naming the project where the orders disagree. A loop
of parents is an error. `tcw project list --json` shows the load order, what
each parent passes down, which children only your personal file lists, and
which projects are read-only from here.

## A project that is not here

A parent or ancestor that is not on this machine, or whose own parents cannot
be read, stops only a command that needs what it passes down. That command
exits with the new code 7 and says which project it needs and how to fetch
it. `tcw validate` reports each such project once, as could not be checked,
and still exits 0.

When a manifest places a project in one folder but the folder search finds it
in another, TCW no longer picks one: every command stops with exit 1 and an
error naming both folders. To settle it, add an entry for that project to your
own `.tcw/tcw-manifest.local.yaml`, which is read first, giving the folder you
mean (for example `lib: ../lib`).

When a manifest entry's folder is missing, the "not on this machine" message
now names the full folder that was checked, not the entry's relative path. In
a linked git worktree, that is the folder beside the main checkout.

## What is gone

- The `projects:` key, with its `parent`, `children` and `upstream` entries.
  A configuration that still has it is refused, with a message saying to name
  parents under `parents:` and children under `children:`. A project that only
  read from another is now a child naming that project as a parent, which does
  not list it back.
- Writing into a sibling, another child of one of your parents: work can be
  created only in a project reached through links both sides declare.
- Filing work into a project not on this machine through a `jira` block.

## `extends`

Until it is replaced in TCW 4.0, `taxonomy.extends` and `capabilities.extends`
may name only an ancestor whose parent links pass that axis down. Naming any
other project is refused, and `extends add` leaves the file unchanged.

## The web app

The create form marks a project that is read-only from here, as the command
line decides it.

The web app has a scope control and a project filter in its header, matching
`--scope` and `--project`, kept in the page's address so a link reproduces the
view. It is shown only for a project that has parents or children. Another
project's objects are shown read-only, marked with whose they are, and
another project's work item names the command that moves it in its own
project (`tcw -C tcw://<owner>.path/ work advance …`); links to
them are followed; a project that could not be read is named above the list;
and each capability row shows how many projects give each status.

## Settings a project takes from its parents

A project now takes its parents' tags and Jira settings: `work.tags` and
everything under `work.jira` come down each parent link that passes `config`,
which every link does unless it says otherwise. Nothing else comes down, and
neither does which backend a project uses: every project says `backend: jira`
itself, and one that says nothing keeps its items in files. So a family of
projects that shares one Jira project writes the site, the fields and the
credential names once, in the parent, and each child writes only its own
backend and stage statuses.

A child changes what it inherits in three ways. Setting a value replaces the
parent's; a mapping merges key by key, so a child that sets only
`work.jira.project` keeps its parent's site. An `inherit: true` entry in its
tags adds to its parents' list:

    work:
      tags:
        - inherit: true
        - mobile

And `null` removes an inherited value. `tcw work tags add` in a child with no
list of its own writes that `inherit: true` entry for you, so the child keeps
following tags its parents add later, and `tcw work tags rm` refuses a tag
that comes from a parent.

## A parent that is not here, or has a mistake

A missing parent stops only a command that needs a setting it could have
given, with exit code 7 naming the setting and the project. Listing, reading,
creating and moving a filesystem project's own items never needs one; applying
or listing tags does, unless the child sets its own tags, and so does every
command on a Jira-mode project whose Jira settings come from that parent.
`tcw validate` never stops: it says the configuration inherited from that
project could not be checked, and still checks the Jira settings the child, or
a parent after the missing one, sets itself. `tcw project config` prints nothing and exits 7
rather than show settings that are not the ones commands run with.

The web app (`tcw serve`) still opens on such a project, and items can still
be created and edited there. Where the tags would be offered, the forms say
why they could not be read and no tag can be chosen, as `--tag` stops on the
command line; an item's existing tags are kept as they are. The board's Tags
filter says the same.

A mistake in a parent's shared settings stops only the commands that read
that setting, naming the parent's file; `tcw validate` in the child warns
about it, and fails only in the parent.

## Personal settings from environment variables

Any setting a personal file may set can now be set from an environment
variable named after the setting and the project, in capitals, with `__`
between them:

    TCW_USER_NAME__MY_APP=Robin
    TCW_WORK_JIRA_CREDENTIALS_EMAIL_ENV__CORE=MY_EMAIL
    TCW_WORK_STAGES_SPEC_PROMPT__MY_APP='[{blob: Keep it short.}, {inherit: true}]'

A list or a mapping is written as YAML. A variable naming a stage changes only
what it names, and a more specific variable wins over a broader one. A
variable stops commands in any project with exit 1 when it names no setting,
names one only the team may set, or holds a value that is not valid YAML, is
`null`, is not the kind of value the setting takes (a list for a stage's
`prompt`), breaks the rules of an `inherit` entry, or is not a valid
`user.name` or credential variable name. The rest of a value is checked only
when the project the variable names is loaded, and stops commands only there:
a binding's shape or keys, a `post` entry, and a `file:` binding that leaves
that project's folder. `tcw validate` reports each problem in the project it
stops, starting with the variable's name. Your settings for
a parent, from its personal file or a variable, reach its children through
what it passes down. `TCW_NO_PERSONAL_CONFIG=1` turns the variables off along
with the personal files. `tcw project config --origin` names the variable a value
came from.

## One name for every object

Every taxonomy entry, capability and work item now has one name, its full
identifier: `<project>.<namespace>/<id-path>`. It says which project owns the
object, which of the three namespaces holds it, and where it sits in that
store:

    demo.taxonomy/invoice
    demo.capabilities/cli/export-a-report
    demo.work/2026-10-22-add-login

Every command prints it: lists print one per line, and `show` starts with the
full identifier and the owning project. Every command that takes an object
accepts its full identifier, its `tcw://` address, or, for an object of the
project you are in, its id-path alone (`cli/export-a-report`). A work item can
also be named by its tracker key, bare (`TCW-67`) or as `<project>.work/<KEY>`.
Letter case counts: a name that differs only in case is not found, and the
message gives the spelling on disk.

A full identifier may name an object in any project TCW can locate, not only
one this project inherits from. Naming a project is not inheriting from it: an
object in a project you do not inherit from can be read but not changed here.

## Links

A link is the full identifier after `tcw://`, never shortened:

    [the export](tcw://demo.capabilities/cli/export-a-report)

A folder is named by a folder address, `tcw://<project>.path/<folder>` for a
folder in that project's root, or `tcw://<project>.<namespace>.path/<folder>`
for one inside its store. `tcw validate` checks every link; a link to a project
that is named but not on this machine is reported as could not be checked.

## JSON output

Every `--json` document now says `"schema": 2`. Records carry `full-id` and
`owner` in place of `slug`, `qualified`, `path` and `origin`.

## Store locations

A `<component>.path` in `.tcw/tcw-config.yaml` is a path relative to the
project or a folder address, which follows the named project wherever its
checkout is:

    work:
      path: tcw://workspace.path/docs/app/work

An absolute path or one starting with `~` is refused in the shared file; a
folder that sits elsewhere on one machine is placed by an entry in
`.tcw/tcw-manifest.local.yaml`. `tcw validate` fails two stores that are the
same folder or one inside the other, in this project or across the projects it
can locate, and a store location that loops.

## TCW 3.x names

Names, links and stored references in their TCW 3.x form (`tcw://C/cli/x`,
`tcw://core/W/<folder>`, `<project>/<folder>`, a reference stored as a bare
path) are no longer read. They are reported as needing `tcw migrate`, which
converts a project. In a project that keeps its items in Jira, a ticket whose
TCW Item field still holds a 3.x value is left out of `tcw work list`, and one
warning says how many were and names `tcw migrate`.

## Web app fixes

Saving a new work item in the web app no longer asks whether to leave
without saving. And after you edit one of an item's stage files, the item's
page opens on that file's tab rather than on the item's current stage.

## Object folders and state files

Each kind of record now has its own named file, and that file is what makes a
folder a record: `tcw-taxonomy.yaml` for a taxonomy entry,
`tcw-capability.yaml` for a capability, and `tcw-work-item.yaml` for a work
item. Each starts with `tcw-version`, so a file written by a newer TCW is
reported rather than misread.

A record's folder holds its own files, the folders of the records below it,
and one `resources/` folder for anything else: diagrams, notes, sample files.
A term's attachments are the files in its `resources/` folder, and a
capability's extra documents are named there too. `tcw validate` reports a
file or folder that does not belong, and a folder whose name is reserved, such
as `resources`.

A folder with no state file can group records in any of the three stores. It
is never listed as a record itself, but its name is part of the name of every
record inside it, so `2026/2026-10-01-add-login` is a work item in a `2026`
folder.

## Nested work items

A work item's folder can sit inside its parent's folder, in either backend,
so the folders read the way the items relate (see "A child's folder goes inside
its parent's" for how a new one is placed). Work
items are found, listed, shown, edited, moved and renamed wherever their folder
sits.

## Parents for terms and capabilities

A term or a capability may name its parent: `tcw taxonomy add --parent` writes
it, and `tcw capabilities add` and `set` take `--parent`. Records and `show`
include it. `tcw validate` reports a parent that names nothing, the record
itself, or a loop, and warns where a record sits in another record's folder
that its parent does not name; the parent is what counts.

## Names stay within 255 characters

No name, project and path together, is longer than 255 characters. A new item's
title words are shortened to fit under a deeply nested parent, and a command
that would need a longer name is refused before it writes anything.

## TCW 3.x files

A folder still holding a TCW 3.x `meta.yaml` or `item.yaml` is not read as a
record. `tcw validate` names each one and says to run `tcw migrate`, and
removing a record with such a folder below it is refused until then.

## Taxonomy and capabilities come from your parents

A project now takes its parents' taxonomy and capabilities through its parent
links, every level up, from each parent whose `inherit` includes them. The
`extends` settings and the `tcw taxonomy extends` and `tcw capabilities
extends` commands are gone. A project whose `.tcw/tcw-config.yaml` still holds
`taxonomy.extends` or `capabilities.extends` is told what to write instead,
and its taxonomy and capabilities commands stop until the key is deleted.

## Changing one inherited entry

To change one entry you inherit, put your own entry at the same path, holding
only what you change; everything else still comes from the parent. `tcw
capabilities set` on an inherited capability does this for you, and so does
`tcw taxonomy add` at a path you inherit. `show`, the JSON records and the web
app say which entry yours overrides. `tcw capabilities reset` and `rm` take
yours away again, and the inherited entry shows through.

An entry of your own that overrides nothing must be complete: a name, a
description file and, for a capability, a status. So a leftover change whose
original moved or was removed is reported by `tcw validate` instead of
quietly standing alone.

When two parents that are not related to each other both have an entry at
one path, the one later in the load order is used, whole, and `tcw validate`
and the listings warn about it until you decide with a complete entry of your
own.

## A parent that is not here

With a parent missing, your own entries can still be listed (`--local`) and
shown, marked as partial, and `tcw validate` says what it could not check.
The commands that need what the parent passes down stop with exit code 7.

## Smaller changes

- Capabilities no longer carry a `cap-` id. A capability is named by its
  path; `tcw validate` reports an `id: cap-…` line left in a capability's
  file.
- Editing a capability's body in the web app changes only that capability's
  own description, so attached documents and an inherited description are no
  longer copied into it.

## Choose which projects a command covers

Every list and show command, `tcw work list|show`, `tcw taxonomy
list|show|search` and `tcw capabilities list|show|search`, takes
`--scope own|up|down|all`. `own`, the default, is the project alone; `up` adds
the projects above it; `down` the projects below it; `all` both. A sibling, a
project that only shares a parent, is never included. `--project <id>` keeps
one of those projects' own results.

`tcw taxonomy list` and `tcw capabilities list` now list only the project's own
entries by default; `--scope up` adds the ones it inherits, as these commands
listed before. `show` of an inherited entry by its path alone needs
`--scope up`, and says so. `list --local` is removed: it stops with a message,
since the default already does what it did.

## A project that is not here is named, not skipped

When a project the scope covers is not on this machine, or cannot be read, the
command still succeeds, and a warning names that project, says what was left
out, and gives the command that fetches it. With `--json`, the document's
`projects` lists every project covered and why any could not be read.

## Each project's status for a capability

Under `--scope down` or `all`, each capability is listed once, with the status
each project gives it: in the JSON as `statuses`, and in
`tcw capabilities show` as a `status by project:` block. Every override of an
entry or capability in those projects is named as `overridden-by`.

## Work across a project's family

`tcw work list --scope down` shows the projects below this one, each with its
own items. An epic's parts filed in other projects show as its children, and
`--parent` finds them. `tcw work show` finds an item by its folder name or
ticket key in any project the scope covers. Projects that keep their items in
one Jira project, and sign in as the same account, are read with one search.
The backlog audit (`tcw work procedure audit-backlog`) covers the projects
below this one, names each item by its full identifier, and reports a project
it could not read as not audited.

## Only the owning project changes an object

Only the project that owns a record can change it. A command run in one project
that would change another project's work item, term or capability stops (exit
3), changes nothing, and says which folder to run it in, or that the owning
project is not on this machine. The rule is the same whatever the projects'
relation. Referring to another project's object, as a parent, a blocker or a
link, is still allowed, and so is overriding an inherited capability.

## Run any command as another project

`tcw -C <folder> <command>`, or `tcw -C tcw://<id>.path/ <command>`, runs any
command as if it had been started in that folder, as that project, with its
settings, checks and hooks. `-C` may be given more than once.

## Filing into another project is replaced

`tcw work new --project` and `tcw work edit --blocks` are removed; each now
stops with a message naming what to do instead. Create a part in its own
project with `tcw -C tcw://<id>.path/ work new "<title>" --parent <epic>`, and
record a blocker on the blocked item with `--blocked-by`. The web app's
project choice on the create form and its "Blocks (add)" section are gone.

## Moving and renaming

New: `tcw work move <item> --into <folder>` or `--top`,
`tcw taxonomy rename|move` and `tcw capabilities rename|move`. `tcw work rename`
now works on an item with items inside it. A move or rename carries everything
nested in the folder with it, updates every reference in this project, prints
one `<old> -> <new>` line per identifier it changed, and lists the places it
could not update. It checks everything before writing, and if it stops partway
it says what it did and that running the same command again finishes it.
References in other projects are not changed: `tcw validate` there reports
them.

## Parents and blockers Jira cannot link

In a Jira project, a parent or blocker that Jira cannot link (an item kept in
files, or a ticket on another Jira site) is now kept in the item's folder
rather than refused, and TCW says Jira will not show it. `tcw validate` checks
those values without reading Jira.

## Project commands move into `tcw project`

Everything about the project itself is now one command group, `tcw project`,
beside `tcw taxonomy`, `tcw capabilities` and `tcw work`:

| Before | Now |
| --- | --- |
| `tcw init` | `tcw project new` |
| `tcw projects list` | `tcw project list` |
| `tcw config show` | `tcw project config` |
| `tcw provision` | `tcw project provision` |

The old commands are gone. Typing one stops with a usage error (exit 2) that
names the command to use instead. Every message, help text and suggestion now
names the new commands, and a mistyped command offers a command that exists
where you typed it before the same word elsewhere, so `tcw work info` still
suggests `tcw work show`.

Two new commands join them. `tcw project path <id>` prints the folder of a
project on this machine, or says it is not here and how to fetch it.
`tcw project info` shows how the current project is put together: its parents
and children, the order its ancestors are read in, where each setting comes
from, where its stores are, and what it overrides, with `--json` for scripts.

`tcw project config --origin` now labels each value with the project, the
layer and the file it came from, such as `# core, project
/home/me/core/.tcw/tcw-config.yaml`, or `# app, environment TCW_USER_NAME__APP`,
or `# built-in`.

## `tcw project provision` fetches connected projects

`tcw project provision` fetches the projects your project is connected to that
are not on this machine, each from the repository its manifest entry gives and
into the folder that entry names, then the projects those name, in turn.
`tcw project provision <id>` fetches one project and the ancestors it needs;
`--component` fetches only stores and never a project; `--dry-run` shows what
the first round would fetch and contacts nothing.

It never overwrites anything. A folder that already holds files, or holds only
`.git` (a clone that stopped part way), is refused before any remote is
contacted, and each clone is made beside its destination, checked, and only
then moved into place, so a failure leaves nothing behind.

A manifest that is not your project's own, such as one in a parent you just
fetched, may place a clone only directly beside that project's repository,
never at or above your home folder and never inside a hidden folder below it.
This keeps a repository you have not read from choosing where on your disk
something is written. When a manifest asks for more, the command says so and
tells you how to place the project yourself.

A store whose `ref` names no branch, tag or commit now fails, where before it
could be read as a file name.

A project already on this machine is never fetched again. If a manifest
fetched during the run would place such a project somewhere else, the run
stops with exit code 1, names the manifest, and says how to keep the project
where it is.

## `tcw migrate` brings a TCW 3.x project to 4.0

TCW 4.0 refuses a project still in the 3.x format and names one command to
run: `tcw migrate`. Run in the project's folder, it converts the project in
place:

- the configuration moves into `.tcw/`, with `projects:` and `extends`
  turned into parent links and manifest entries;
- every term, capability and work item gets its 4.0 state file, and the
  capability ids TCW 3 used are kept in `.tcw/tcw-migration.yaml`, so
  references to them still resolve; keep that file, and keep it in a
  library other projects read;
- files TCW 3 kept loose beside an object move into its `resources/`
  folder, and links to them are rewritten;
- an override moves to the path of the capability it overrides;
- references and links get the project that owns what they point at;
- in a project that keeps its work in Jira, each ticket's `TCW Item` is
  rewritten to the 4.0 form, and only that field.

`tcw migrate --dry-run` lists every change, ticket edits included, and
writes nothing. `tcw migrate --no-jira` converts the files and leaves the
tickets for a later run. Nothing is written until the whole plan is known
to be possible; a problem that stops it is listed with how to fix it. The
report also lists what needs your attention and what TCW 4.0 will read
differently from TCW 3.

If a run is stopped partway, run `tcw migrate` again: it finishes what was
started. Until it has finished, do not commit the files. Commit or back up
before a real run.

In a family of projects, migrate each one, parents first; each run names
the related projects still in the 3.x format and the command to migrate
each. Everyone working on a project upgrades together; when someone else
has already migrated and committed, your own `tcw migrate` converts what
is still yours: your personal settings and, for a project TCW 3 cloned
for you, an entry pointing at that clone.

TCW 4.0 does not let the shared files name a related project by an
absolute path (or one starting with `~`), since such a path is only right
on one machine. When the TCW 3 configuration did, the person who migrates
gets that path in their own `.tcw/tcw-manifest.local.yaml`, which is not
committed, and the run lists it under "needs attention" (A14). Everyone
else adds their own entry to their own `.tcw/tcw-manifest.local.yaml`;
their `tcw migrate` cannot do it for them, because the path is no longer
in any shared file.

## Moving from TCW 3.x: the migration guide

The 3.x to 4.0 migration guide, `docs/migration-guide-3.X-to-4.0.0.md`, says,
step by step, what to do before running `tcw migrate`, how to run it and read
what it prints, the order to migrate related projects in, and what replaces
every 3.x command, flag, setting, file and name. It also shows, one step at
a time, how a large item split into parts (an epic) gets a part in another
project in 4.0, for an agent taught the 3.x way, where the part was filed into
the other project's inbox from the epic's own project.

## The documentation and the skills describe TCW 4.0

The README, the guides, the use cases and the plugin's skills now describe
TCW 4.0: full identifiers, parent links and manifests, `--scope`, `--project`
and `-C`, the `.tcw/` folder, renaming and moving objects, and personal
settings and environment variables. The guide on working across repositories
is now "Related projects", `docs/guide/multi-repo.md`.

## A child's folder goes inside its parent's

`--parent` on `tcw work new`, `tcw taxonomy add` and `tcw capabilities add`
now puts the new folder inside the parent's folder whenever the parent is one
of your project's own, so `tcw work new 'Part' --parent 2026-10-01-epic` makes
`2026-10-01-epic/<date>-part`. A capability's path is read inside the
parent's folder:
`tcw capabilities add bulk --parent billing/invoices` makes
`billing/invoices/bulk`, and `billing/invoices/bulk` still works as written;
a deeper path, such as `extra/bulk`, is refused, naming the capability to give
as `--parent` instead.
To keep the folder where it would be without a parent, add `--flat`, or in
the web app tick **Keep its folder at the top of the work folder**. A parent
that is inherited, or belongs to another project, cannot hold the folder: the
command says so, and makes it as `--flat` would.

## Fixes

- When TCW refuses a `tcw://` address, the error now quotes the address you
  wrote, `tcw://` included.
- A store location or `tcw -C` target written `TCW://…` now gets the address
  error that says what is wrong, instead of a confusing "not a directory" or
  "no such folder".
- `tcw validate` names `.tcw/tcw-config.yaml` once, not twice, when a store
  cannot be opened.
- `tcw capabilities set --parent` now refuses a parent that would make the
  capability its own ancestor, instead of writing it and leaving
  `tcw validate` to find the loop.
- `tcw validate` on a TCW 2.x work store points you to the 2.8-to-3.0
  migration guide, since `tcw migrate` does not convert 2.x.
- With two override variables setting one stage's prompt, the note on
  standard error names only the one whose prompt is used.
- `tcw capabilities rm` no longer removes a capability that another one names
  as its parent; it refuses and names the one to repoint first.
- Removing the last capability or term in a folder now removes the empty
  folder too, so `tcw validate` no longer warns about it afterwards.
- When you migrate a project before its parent, `tcw migrate` now says that
  its check of the result stopped at the parent, and asks you to run
  `tcw validate` once the parent is migrated.
- `tcw migrate` lists the related projects still to be migrated with parents
  first, in the order to migrate them.
- `tcw migrate`'s summary uses the singular for a count of one.
- Refusing a `tcw://` address given to `tcw project new --work-path`, TCW now
  names `tcw project new` rather than an `init` command that no longer exists.
- `tcw project config --origin` now says which environment variable a skipped
  Jira credential name came from.
- Inside a project that already has an ID, the advice for adding a taxonomy or
  capabilities store no longer asks for `--id`.
- `tcw project provision` no longer says "Nothing to provision" before going
  on to fetch the projects it names; it says there is no store to fetch.
- The migration guide now says that a dry run in a project whose work is kept
  in Jira needs the Jira credentials, or `--no-jira`.
- Git worktrees made one inside another, such as a child repository's
  worktree inside its workspace's worktree, now read the workspace and its
  stores in those worktrees, not in the folders they were made from, so
  `tcw migrate` and every other command in such a copy change only the copy.
  `tcw migrate` refuses (B19) a run that would still change another checkout,
  and names files outside the project's folders by their full paths.
