# v3.0.0

TCW 3.0 describes a project's work with one model. A work item is a folder that
never moves; its stage is a property recorded about it, and one command,
`tcw work advance`, moves it from stage to stage. The work can be kept in the
repository or in Jira: with Jira, people outside engineering read and change the
request, status and assignee there, and the repository keeps the technical
record. Every command follows one output contract, with fixed exit codes, and
TCW never changes git state: committing and pushing are your project's choice.

This is a major release with breaking changes. Commands, configuration keys and
the layout of the work folder have all changed, and TCW 2.x projects do not
work with 3.0 until they are moved over. To move an existing project, follow
[the 2.8 to 3.0.0 migration guide](../migration-guide-2.8-to-3.0.0.md) with
an agent.

## Upgrading

- **Moving a 2.8 project to 3.0.0.** A 2.x project does not work with 3.0
  until it is moved over: 3.0 refuses a 2.x `tcw-config.yaml` and does not
  read a 2.x work folder. [The 2.8 to 3.0.0 migration guide](../migration-guide-2.8-to-3.0.0.md)
  walks you and an agent through it, under any agent harness, using only a
  shell, `curl` and `tcw`, and, for a Jira project, `jq`. It converts the
  configuration, the board, your own scripts and documents, and, for a Jira
  project, binds every item to its ticket. You approve one plan before anything changes, the agent stops only
  where it needs you, and every 2.x name has a row saying what it becomes.
  Its last step goes through the instructions and memories your agents have
  been given and asks you what to do with each one that still describes
  2.x. A project older than 2.8 upgrades to 2.8 first.
- **TCW was moved first.** TCW's own repository was migrated by following
  the guide as written, with its work in the Jira project `TCW`, before
  3.0.0 was released, and the guide was corrected wherever that run found
  it wrong.

## Work items, rebuilt

The `tcw work` commands now run on TCW 3.0's simpler work model. This is part
of the 3.0 release; the migration guide that comes with it explains how to
move a project across.

- **An item is a folder that never moves.** Its stage is written in its
  `item.yaml`, so a link or a path to an item keeps working for the item's
  whole life, finished or not.
- **One command moves an item: `tcw work advance`.** It moves the item to its
  next stage, runs that stage's checks first and refuses the move if one
  fails, and `--dry-run` tells you what would happen without moving
  anything. Skipping a stage or overriding a failed check needs `--force` and
  a reason, which is kept with the item.
- **Comments.** `tcw work comment` records a dated remark on an item. Forced
  moves and discards leave their reason as one.
- **`tcw work discard --reason`** closes an item that will not ship.
- **`tcw work rename`** renames an item's folder and updates every other item
  in the project that names it.
- **File work in another project** with `tcw work new --project <id>`. It
  lands in that project's inbox, and the files are left for its owners to
  commit.
- **The inbox is a stage.** `tcw work new --stage inbox` files a raw request,
  and `tcw work list --stage inbox` lists them.
- **TCW no longer commits, pulls or pushes your work items.** Every change is
  left in your working tree for you to commit, as with any other file.
- **Priority** is now a named level, from `lowest` to `highest`.

Removed, with the 2.x work store: `start`, `submit`, `rework` and `complete`
(use `advance`), `drop` and `delete` (TCW never deletes an item), `inbox`,
`tracker`, `tombstone`, `reconcile`, `delegate`, `escalate`, `scaffold`, and
`stage gate` and `stage validate` (use `advance --dry-run`). The
configuration keys `work.lifecycle`, `work.tracker`, `work.retain`,
`work.auto-commit-transitions`, `work.publish-transitions` and
`work.trunk-branch` are now refused with a message naming the migration
guide. Jira support comes back, rebuilt, later in 3.0.

`tcw serve` does not show work items for now; its work view is being rebuilt
on the new model.

## Jira as the home of your work items

A project can now keep its work items in Jira. Set `work.backend: jira` and a
`work.jira` block in `tcw-config.yaml`, and each item is a Jira ticket: Jira
holds its stage, its request, its comments, and its assignee, priority,
estimates, labels, parent and blocking links. The repository keeps only the
technical record — specs, plans and implementation rounds — in one folder per
ticket, named after the ticket's key. This replaces the 2.x `work.tracker`
connection, which is gone; the migration guide explains how to move across.

- **Each stage is one Jira status.** `tcw work advance` makes exactly one
  workflow transition, and any reason you give lands on the ticket as a
  comment in the same step. QA happens on the ticket: leaving QA asks for a
  reason, and nothing is written in the repository for it.
- **New items start as tickets.** `tcw work new` creates the ticket first and
  its folder second. A ticket key works anywhere an item is named, so
  `tcw work show TCW-67` finds the item.
- **Tickets filed in Jira become items with `tcw work tickets adopt <KEY>`.**
  `tcw work tickets list` shows the ones waiting. If an adoption or a `new`
  stops part way, running `adopt` again finishes it.
- **File work into a Jira-mode project from another project** with
  `tcw work new --project <id>`. The ticket lands in that project's Jira
  inbox; a `jira` block in your `connected-projects` entry describes a
  project that is not on this machine.
- **`tcw validate --remote` checks a Jira project against your configuration,**
  reading only: the fields TCW needs on each screen, every stage's status,
  and that the workflow offers one transition for every move TCW makes. It
  also checks each item folder against its ticket. Plain `tcw validate` never
  contacts Jira.
- **TCW never commits for you in Jira mode.** The item folders it writes are
  left for you to commit.

## Personal configuration, and telling TCW who you are

You can now shape TCW to the way you work without changing what your team
gets. Two files hold your own settings, and neither is shared:

- **`~/.config/tcw/config.yaml`** (or `$XDG_CONFIG_HOME/tcw/config.yaml`)
  applies to every project you work in.
- **`tcw-config.local.yaml`**, beside a project's `tcw-config.yaml`, applies
  to that project only. `tcw init` adds `/tcw-config.local.yaml` to the
  project's `.gitignore`, and `tcw validate` warns if the file is tracked by
  version control anyway.

TCW reads its own defaults, then `tcw-config.yaml`, then the user-wide file,
then the local file; a later file wins.

- **What your files may set:** `user.name`, a stage's `prompt` and `post`
  lists, a procedure's list, and the names of the environment variables
  holding your Jira credentials. Anything else belongs to the team: a personal
  file that sets it is an error naming the file and the key, and every command
  stops on it until it is removed. Set `TCW_NO_PERSONAL_CONFIG=1` to run with
  neither file.
- **Add to a list instead of replacing it** with an `inherit: true` entry,
  which stands for the list the file below produced. `[{blob: "my note"},
  {inherit: true}]` puts your note above the team's instructions and keeps
  them.
- **`inherit: true` replaces `builtin: true`** in `tcw-config.yaml` too, where
  it stands for TCW's own text. Writing `builtin: true` is now an error that
  points to the migration guide.
- **`tcw config show`** prints the configuration a command actually runs
  with, all files merged. `tcw config show --origin` names the file each value
  came from and lists anything your files set that was not used; it still
  prints when something is wrong, so you can find the line to fix. A value
  under a key ending in `-env` that does not look like a variable's name is
  printed as `(value not shown)`, in case a token was pasted there.
- **Who you are.** Set `user.name` in either personal file; in a Jira project
  you are the account your credentials belong to. `tcw work list --mine` lists
  the items assigned to you, and `--assign-me` on `tcw work new` and
  `tcw work edit` assigns one to you. `TCW_WORK_OWNER` and your version
  control name are no longer read for this.
- **Your own files and scripts.** A `file:` path is read relative to the file
  that names it, and a command or script from any file runs with
  `TCW_CONFIG_DIR` set to that file's folder. When your files changed a
  stage's or procedure's text, `tcw work stage prompt` and `tcw work
  procedure` say so on stderr, and a failed `post` command names the file it
  came from.

## One command surface and one output contract

Every `tcw` command now follows the same rules, so a script or an agent can
rely on what it prints and what its exit code means. The full table of renamed
and removed commands is in `docs/migration-guide-2.8-to-3.0.0.md`.

- **stdout carries only what a command produces.** `tcw work new` prints the
  new item's full slug, `tcw taxonomy add` and `tcw capabilities add` print the
  new entry's path, list and search commands print one path or slug per line,
  and a command that only changes something prints nothing. Everything said to
  a person — progress, warnings, errors — goes to stderr, and every file a
  command writes or removes is named there (`wrote …`, `removed …`). Every
  `--json` output is one object that starts with `"schema": 1`.
- **Exit codes mean one thing everywhere:** 0 OK, 1 an error, 2 a malformed
  command or value, 3 refused, 4 not found, 5 Jira or a declared project could
  not be reached, 6 the item moved but something after the move failed.
  `tcw --help` lists them.
- **Every command's `--help`** ends with what it prints and what it writes,
  and gives examples. Options have one long spelling each; the short ones
  (`-s`, `-p`) are gone.
- **`tcw validate` prints its findings on stdout,** one per line as
  `error: …`, `warning: …` or `unresolved: …`, with the count on stderr. Only
  an error fails the run. It checks the project you run it in; it no longer
  walks into child projects, and its path argument and `--no-recurse` are gone.
- **Renamed and removed commands.** `tcw work nodes` is now `tcw projects
  list`. `tcw <axis> init` is `tcw init <axis>`. `tcw taxonomy check` and
  `tcw capabilities check` are part of `tcw validate`. `tcw work procedure
  prompt <name>` is `tcw work procedure <name>`. `tcw capabilities extends
  <id> [--rm]` is `tcw capabilities extends add|rm <id>`, and `capabilities
  list --local-only` is `--local`. The `tcw taxonomy <path>` and
  `tcw capabilities <path>` shorthands are gone; use `show`.
- **`tcw taxonomy add` reads its description from stdin only,** as
  `tcw capabilities add` reads its body.
- **Taxonomy and capability edits are no longer staged in git.** They appear as
  ordinary unstaged changes; commit them yourself, or with a `post` hook.
- **`tcw provision --refresh` is gone.** `tcw provision` obtains what is
  missing and never fetches into a checkout you already have.
- **`connected-projects:` in `tcw-config.yaml` is now `projects:`,** with the
  same `parent`, `children` and `upstream` entries. Every command refuses a
  config that still has the old key, with an error that names the migration
  guide.
- **The capability fields `Planning doc` and `Tracker` are retired.** Setting
  either is refused, and `tcw validate` reports a record that still has one.

## Instructions for the new stages

Everything TCW tells an agent now describes the 3.0 stages, and each piece of it
lives in one place.

- **Every stage has built-in instructions,** including the new `review` and
  `qa`: `tcw work stage prompt <stage> <slug>` prints what the stage is for,
  what it reads, what it writes and where, and how to finish. A stage that
  moves the item on ends with the `tcw work advance` command to run; inbox,
  postmortem, and the stages Jira keeps (request and qa there) end without
  one, because a person or the backend moves the item. Review and qa write a round whose
  `verdict` and `judges` decide where the item goes. Where your project keeps
  its work in Jira, the request and qa instructions describe the ticket rather
  than files.
- **No instruction tells an agent to commit, push, branch or use a worktree.**
  How your changes are saved and shared is your project's business; add it to
  a stage's instructions under `work.stages.<stage>.prompt` if you want it
  followed.
- **Capability records change with the code.** The `capabilities` skill now
  has the agent declare capability changes in the item's `capabilities.yaml`
  during spec, and add or edit the records themselves during implement with
  the status they really have (`--status Supported`). Moving out of implement
  checks they are there; nothing is flipped at completion.
- **Pausing work** writes the handoff in the folder of the stage the item is
  at (`tcw work path <slug> <stage> --handoff`), or as a `Handoff` comment where
  Jira keeps the stage, and no longer commits or pushes. What the handoff
  holds comes from the new `pause-work` procedure, which your project can
  replace.
- **The procedures are** `unattended-work`, `triage-issues`,
  `documentation-sync`, `create-work`, `audit-backlog`, `search` and
  `pause-work`. `post-mortem`, `consolidate-plans`, `decompose` and
  `delegation` are gone: the postmortem stage has its own instructions, and
  splitting and filing into another project are described in the `work`
  skill. A configuration that still names a removed id is refused by
  `tcw validate`, which says where that procedure's text went.
- **Skills removed:** `work-stage` (read `tcw work stage prompt` instead),
  `commands-verify-work` (review and qa replace verify) and `post-mortem` (use
  the postmortem stage). The `verifier` and `post-mortem` agents are replaced
  by a `reviewer` agent that reads the review stage's instructions.
- **The `setup` skill** can now walk you through configuring a project to
  keep its work in Jira (`backend: jira`), checking the workflow with
  `tcw validate --remote`. It configures the backend; it does not move
  existing items, so finish or discard the items kept as files first.

## The web viewer, rebuilt: one process, no Node.js

`tcw serve` is now a single Python process. Node.js is no longer needed to
run it: the browser client comes prebuilt inside the package, as before, and
the server that hands it to the browser is part of TCW itself.

It serves the project it is started in, and it is built for TCW 3.0's work
model:

- **The work board** filters by stage, tag and assignee, hides finished and
  dropped items until you ask for them, and sorts by name, creation date or
  priority.
- **An item's page** has a tab for each stage that keeps files, showing that
  stage's document, or its rounds with their verdicts, and handoffs. You can
  write each of them in the browser, start a new round or handoff, and edit
  the item's declared ledger changes as a form.
- **Properties and comments** can be edited and added in a project whose work
  is kept in files, and new items can be created here or in a connected
  project.
- **Every field suggests what it can hold.** Tags come from the registry,
  references from the entries that exist, inherited ones included, and
  typing `tcw://` in a document offers every object to link to. A value that
  names nothing is refused before anything is written; another project's
  item can be named, with a warning that the page cannot check it.
- **In Jira mode** the request, comments, stage and properties are shown
  read-only with **Open in Jira**, while the item's files stay editable, even
  when Jira cannot be reached. A **Tickets** view adopts inbox tickets.

The viewer no longer moves items between stages. Each item's page names the
command that does: `tcw work advance <slug>`, or `tcw work discard` to drop
one. It never changes git state.

It no longer shows child projects' items on the same board; open each
project's own viewer instead. Every request is now checked to come from your
own machine, reads included.

Two more things that worked in 2.x no longer do:

- **Inherited taxonomy entries and capabilities cannot be edited in the
  viewer.** In 2.x, saving an inherited capability made a local override. Now
  run `tcw capabilities set <path> --field <name>=<value>`, which makes the
  same override; an inherited taxonomy entry is changed in the project that
  keeps it.
- **2.x links to a work item, `/<project>/work/<slug>`, no longer open it**;
  they open the board. An item's link is now `/work/<folder>`.

## Fixes

- **A note that may already be on the ticket is not suggested twice.** When a
  move in a Jira project records its note as a separate comment and the
  connection fails while posting it, TCW now reads the ticket's newest
  comments first. If the note is there, nothing is reported. If the comments
  cannot be read either, the message says the note may have been posted and
  to check with `tcw work show <slug>` before adding it with
  `tcw work comment`. Only a comment that arrived after the note was sent
  counts, so an older note with the same words (the same move, made before)
  no longer hides one that never arrived.
- **Your Jira token is sent to your Jira site only.** If the site answered a
  request with a redirect to another address, the token went along with the
  redirected request. It no longer does. If the redirected request is then
  refused, the message says Jira redirected it to that address and that
  `work.jira.site` should be the address Jira answers at, rather than blaming
  your credentials.
- **`tcw provision` with a `tcw-config.yaml` it cannot read** now reports the
  error, naming the file, and exits with code 1. It used to say "Nothing to
  provision" and succeed.
- **`tcw work new --project <id> --stage inbox`** is refused (exit code 2):
  `--stage` was dropped without a word. An item created in another project
  starts where that project's intake puts it: its inbox, or, in a Jira
  project, as a ticket waiting in Jira for `tcw work tickets adopt`.
- **A Jira site address that is not a Jira site** is now reported as that
  (exit code 1, asking you to check `work.jira.site`) instead of "not found".
  A ticket or project that does not exist is still exit code 4.
- **A `tcw-config.yaml` that is not valid UTF-8 text** is reported naming the
  file and the byte, by `tcw provision` and `tcw init` as by the other
  commands, instead of in Python's own words, which named no file.
- **A configuration key written as a list or a mapping**, such as `? [a]`,
  is now an error that names the file and line, instead of a crash.
- **Both bad Jira credential settings are reported**, when `email-env` and
  `token-env` are both wrong, not only the first.
- **`tcw config show` writes binary, set, ordered-map and pairs values
  correctly**, each reading back as the same value. A value it cannot write
  that way is reported as an error naming its key, instead of being printed
  wrong.
- **`tcw work new --stage inbox` in a Jira project** is refused at once, without
  waiting for text on standard input.
- **The retired `connected-projects` key** is reported with the path to the
  file from the folder you ran the command in, such as `../tcw-config.yaml`.
- **The work commands now check the whole project graph**, as `tcw taxonomy`
  does: `tcw work list` refuses when a child project's `tcw-config.yaml` still
  uses a retired key, naming that file. A child project that is declared but
  not on this machine still does not stop it.
- **The refusal for a work store outside git** reads "the work store of
  project '<id>' is not in a git repository".

## Changes in what commands accept

- **`tcw taxonomy add --slug`** must already be a slug: lowercase letters and
  digits in words joined by single hyphens. A space, a capital letter or a
  `/` is a usage error (exit code 2) and nothing is created; to nest an entry,
  use `--parent`. The web viewer refuses the same slugs when it creates a
  term.
- **`tcw capabilities reset`** refuses (exit code 3) when a capability sits in
  a folder under the override's, instead of deleting it with the override.
  The message names each one; remove local ones with `tcw capabilities rm`
  and nested overrides with `tcw capabilities reset` first.
- **`tcw provision` does not ask for anything** while it clones: no
  password, no ssh passphrase, no question about trusting a new server. Where
  an answer would be needed the clone fails with git's reason. A private
  repository needs a credential helper that already holds its credentials,
  or an ssh key loaded in an ssh agent. The exception is an ssh command you
  have set yourself (`GIT_SSH_COMMAND`, `GIT_SSH`, or `core.sshCommand` in your
  global or system git config or given on the git command line, not the
  current repository's own setting): TCW leaves it alone, so ssh may still ask.
- **Offline `tcw validate` in a Jira project** now reads each item folder's
  `capabilities.yaml` and reports one that cannot be read or is malformed.
  With `--remote` it is reported once, not twice. Checking a single item,
  and saving a file in the web viewer, report it too, whatever the item's
  stage. A `qa` folder's rounds,
  which Jira keeps, now get only the "this folder is ignored" warning.

## Unattended work

- **At the request stage, an unattended run does not ask the advisors** what
  the requester wants, since that is not theirs to know. It writes the
  request from the evidence available and marks each assumption it made.
  Where the backend keeps the request, as Jira does, it posts its questions
  with `tcw work comment` instead and leaves the request's text alone. The
  unattended-work procedure has a row for this, and the autonomous-work
  skill states the same rule.

## The web viewer

- **Saving a taxonomy term or a capability needs its revision.** A save that
  does not say which version it was edited from is refused, so it can never
  overwrite someone else's change unseen. The viewer's own page always sends
  it.
- **An item's files stay inside the item's folder.** When a stage folder or
  `capabilities.yaml` is a link that leads outside the item folder, the
  viewer neither reads nor writes through it. On the item's page, a document
  or declaration reached through such a link is shown as not written, and
  rounds and handoffs reached that way are left out, so they decide no
  verdict.
- **The "stale write" banner** no longer makes the browser warn about its
  layout.
