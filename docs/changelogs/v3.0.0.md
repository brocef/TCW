# v3.0.0

## Added

- The filesystem work backend for TCW 3.0 (TCW-70), wired into `tcw work`.
  - `tcw/work/fs_backend.py`: `FsWorkBackend`, implementing TCW-69's
    `WorkBackend` over item folders that never move. Each item's properties
    live in `<item>/item.yaml`; comments are `comments/<UTC timestamp>.md`;
    `read_all` returns the readable items and the unreadable ones apart.
    Nothing is staged or committed.
  - `tcw/work/open.py`: `open_backend`, `open_project` (another project,
    by id, through the registry) and `delegate`, with the conditions on the
    target project: declared, not upstream, present, with a work store, and
    with no uncommitted changes in it, read with `--no-optional-locks`.
  - `tcw/work/record.py`: the item record shared by `show --json`,
    `list --json` and the `generate:` payload.
  - `tcw/findings.py`: `Finding`, the shape `tcw validate` prints.
  - New commands: `tcw work advance [--to] [--force --reason] [--dry-run]`,
    `discard --reason`, `comment` (text on stdin), `rename <slug>
    <new-words>`, `path <slug> [<stage>] [--next|--handoff]`,
    `new --project`, `new --stage inbox`, `edit --blocks`.
- `tcw work list` filters: `--stage`, `--tag`, `--parent`, `--assignee`,
  `--all`, `--json`.

- The Jira work backend for TCW 3.0 (TCW-71), in `tcw/work/jira/`.
  - `backend.py`: `JiraBackend`, TCW-69's `WorkBackend` over Jira tickets,
    with folders named `<KEY>-<words>` holding only `item.yaml` with the
    ticket link. Field ids are resolved by display name from the configured
    issue type's create metadata. `set_stage` makes one transition chosen by
    a fixed rule (the lone candidate, else the one whose screen asks for
    nothing but a comment, else a refusal) and decides what happened after a
    400 or a dropped connection by reading the status back. A note for a
    transition with no screen is posted as its own comment after the move,
    because Jira accepts and silently discards a comment sent with such a
    transition (found by the live check). Reads fall back
    to direct reads for any key a search did not return. Offline checks
    (`jira_store_problems`, `link_exists`) never contact Jira.
  - `config.py`: `JiraConfig` and the connected-project `jira` block.
  - `mapping.py`: text to Atlassian Document Format and back as a pair that
    round-trips, and the field mapping in both directions.
  - `jql.py`: the only place JQL is built; TCW Project is matched exactly
    after a search, never with `~`.
  - `tickets.py`: the Jira inbox, adoption, and delegation into a Jira-mode
    project.
  - `remote.py`: the checks behind `tcw validate --remote`. Parent is not
    required on the edit screen of the top-level issue type (an Epic), which
    Jira gives no Parent field.
- Commands: `tcw work tickets list [--json]`, `tcw work tickets adopt KEY`,
  `tcw validate --remote`.

- `tcw/config.py`: the layered configuration loader (TCW-72).
  `load_config(root, *, personal=True)` merges the built-in layer,
  `tcw-config.yaml`, the user-wide file and `tcw-config.local.yaml`, and
  records each value's origin (`Origin(layer, file)`), what personal files set
  that was refused or skipped, and every problem as `Problem(file, key_path,
  message)`. `PERSONAL_KEYS` is the allowlist of what a personal file may set.
  `effective(root)` keeps the acting project's result for the rest of a
  command.
- `tcw.errors.ConfigError` (exit 1), raised for any configuration problem.
- `tcw config show [--origin]` (`tcw/config_cli.py`).
- `tcw work list --mine`, and `--assign-me` on `tcw work new` and
  `tcw work edit`, through the backend's `current_user()`.
- `TCW_CONFIG_DIR` in the environment of every `command` and `generate`

- `Outcome.post_failures` and `tcw.work.hooks.HookFailure`: a failed `post`

## Changed

- `route_capability_path` and `Route` moved from `tcw/work/recursion.py` to
  `tcw/work/gates.py`; `recursion.py` imports them back, so behavior is
  unchanged.

- `tcw work` is `tcw/work/cli.py`, rewritten on the 3.0 model. Every
  `TcwError` exits with its own code (1 error, 2 usage, 3 refused, 4 not
  found, 5 unreachable, 6 moved with a problem).
- `tcw validate`: the work checks run over `item.yaml` files — unreadable
  items, references to items that do not exist (a warning), references into
  projects that cannot be reached (`unresolved:`), stages not in the table or
  disabled, mid-work `capabilities.yaml` problems, and a work store shared by
  two projects. The summary counts only failures.
- `tcw capabilities drift` reads finished items' `capabilities.yaml` through
  `drift_problems`; it no longer reads `Planning doc`.
- `tcw://W/…` references resolve through the backend, by folder; a finished
  item resolves like any other.
- `tcw init` and `tcw work init` make one empty work folder with a
  `.gitkeep`, and no status folders or ignore rules. Moving a store refuses
  when the old one holds an item folder.
- `tcw work tags add` and `rm` write `tcw-config.yaml` without staging it,
  and work outside a git repository.
- `tcw work stage prompt` composes from `work.stages` and adds the stage
  header line itself. The packaged `spec` and `plan` prompts use
  `{{tcw:request}}` in place of `{{tcw:body}}`.
- The `generate:` payload is the 3.0 item record.
- `RESERVED_PROJECT_IDS` is `t`, `c`, `w` and `local`: the 2.x status names
  are valid project ids again.
- `STORE_CLASSES["work"]` is `WorkLocation`, which finds the work folder and
  nothing more.

- `tcw/work/jira/client.py` (moved from 2.x by TCW-70): `search` returns
  every page, takes a field list and an optional limit; `create_issue` takes
  any fields; `apply_transition` takes an optional comment; `comments(key,
  limit)` replaces `recent_comments`; new `edit_issue`, `add_link`,
  `delete_link`, `user`, `assignable_users`, `project`, `project_statuses`,
  `create_metadata`, `edit_metadata`, `link_types`, `workflows`. A
  `Transition` carries `has_screen`, read from Jira's `hasScreen`. `assign` and
  `description` are gone. Error messages name `work.jira`.
- `open_backend` returns a `JiraBackend` for `work.backend: jira`;
  `open.delegate` delegates into Jira-mode projects; `open.reference_resolver`
  answers references into other projects for both `validate` paths.
- `advance.run_post` is a public function, so adoption runs the request
  stage's `post` hooks.
- `cli.resolve_item` accepts a ticket key in Jira mode.
- `TcwError` has an optional `name`, printed by `new` when set.
- `tcw validate`: Jira-mode projects get folder checks offline, and a
  filesystem reference into a Jira-mode project is answered from its folders.

- Every command checks the whole configuration before it runs (in
  `tcw.cli._dispatch`), except `init`, `provision`, `validate` and
  `config show`. `open_backend` builds the acting project's backend from the
  merged configuration; another project's backend ignores personal files.
- TCW's own prompt and procedure text comes only from the built-in layer's
  `{builtin: true}` entries. The fallbacks in `tcw/work/resolve.py` and
  `tcw work lifecycle` are gone, so an empty list really is empty.
- A chain list's `inherit: true` entry replaces `builtin: true` in files;
  `builtin:` written in a file is an error.
- Configuration key paths carry list indexes as integers and print as
  `work.stages.spec.prompt[2]`.
- A `file:` binding is read relative to its declaring file's folder and may not
  leave it; this is checked when the configuration loads.
- `tcw validate` reports configuration problems from every layer first, once
  each; the work checks no longer repeat them.
- The duplicate-key YAML loader exists once, in `tcw/store/yaml_source.py`.
- `JiraBackend.current_user()` returns None only when the credential variables
  are unset. When Jira cannot answer it raises, as every other operation
  does: `Unreachable` (exit 5) when Jira cannot be reached, `BackendError`
  (exit 1) with Jira's reason otherwise. TCW-71 returned None with a warning.
- `tcw config show` prints `(value not shown)` for a value under a key ending
  in `-env` that is not shaped like an environment variable's name.
- Several configuration problems are printed one per line, each with the
  command's `tcw <words>: ` prefix.

- `tcw validate` prints findings on stdout graded error, warning or
  unresolved, with the count on stderr, and checks only the current project.
- The taxonomy and capabilities commands print only their product on stdout,

- `tcw capabilities drift` prints `<kind>: <path>: <message>` lines and checks

- `tcw init` and `tcw provision` say everything on stderr.

- `tcw serve` is one Python process (TCW-77). `tcw/serve/` is rewritten:
  `server.py` (a `ThreadingHTTPServer` that serves the packaged client from
  `tcw/serve/dist/client` with a fallback to `index.html`, and the JSON API),
  `work.py` (the work routes), `files.py` (an item's files and its
  declaration), `records.py` (taxonomy and capabilities) and `services.py`
  (the operations the routes call, replaceable in tests). The only processes
  it starts while answering are `git rev-parse` and
  `git --no-optional-locks status` reads, and the request stage's `post`
  hooks when a Jira ticket is adopted (as `tcw work tickets adopt` runs them);
  at startup `webbrowser.open` starts the system's browser opener unless
  `--no-open` is given.
- Every request, reads included, must name a loopback address in `Host` and,
  when sent, in `Origin`; writes must be JSON of at most 1 MiB. Every answer
  carries `Content-Security-Policy: default-src 'self'`. Errors are
  `{"error", "code"}` mapped from `tcw/errors.py`'s classes, with no
  traceback.
- The API serves one project. `GET /api/project` gives the stage table, the
  record owner (`local` or `backend`), tags, scales, people and the user.
  `GET /api/work` takes `all` and `tag`, as `tcw work list` does, and
  falls back to the item folders on disk (`fallback: true`) when the backend
  cannot be read. Item routes are keyed by folder.
- Files: `GET`/`PUT /api/work/<folder>/files/<path>` with a SHA-256 revision
  (409 `stale-revision` on a mismatch; `null` creates), `POST …/files` for
  where a new document, round or handoff goes and its starting text, and
  `GET`/`PUT …/declaration` for `capabilities.yaml` as six lists. Saves return
  the offline validation findings as `warnings`.
- `PATCH /api/work/<folder>` sends `{changes, expected}` and answers 409 when
  a changed property no longer holds the expected value. `POST …/comments`,
  `POST …/blocks` (one target per request), `POST /api/work` (in this project,
  at the inbox stage, or delegated to a connected one), `GET /api/tickets` and
  `POST /api/tickets/<key>/adopt` call the same operations as the CLI; adopt
  answers `{slug, code, problem}`, with `problem` naming a failed `post` hook.
  In Jira mode the item record, request and comments are read-only (403), a
  new item's assignee must be an assignable account ID (400 otherwise), and a
  blocker must be an item of this project.
- `GET /api/options/assignee` and `GET /api/options/work` give suggestions the
  client cannot compute: Jira's assignable users, and items of connected
  filesystem-mode projects found on this machine.
- Taxonomy and capability edits refuse an inherited entry (403) and a
  capability subject that is not a vocabulary entry (400).
- The client is rewritten for the 3.0 work model: stage tabs from the stage
  table, rounds and verdicts, handoffs, the declaration form, properties,
  comments, the new-item form, the Tickets view, and reference fields that
  refuse, warn on or allow a value that is not a suggestion. The Markdown
  editor completes `tcw://` links.
- `layout.item_folders()` lists the folders under the work path without
  reading them, and every work backend gains `is_item_folder(folder)`, its
  own offline rule for which of them are items (filesystem: a dated name
  holding `item.yaml`; Jira: a name starting with a ticket key), so a stray
  folder is never treated as an item.
- `tickets.adopt` takes a `report` callable for what it tells the user
  (stderr by default), and `tickets.is_assignable(backend, account_id)` checks
  one account through the assignable-users search's `accountId` parameter.
- An unexpected `ValueError` in a route is now a 500, not a 400.

- `JiraBackend._post_note`: a `TrackerUnavailable` is followed by a read of the
  newest `NOTE_WINDOW` comments; found is success, not found is
  `MovedWithoutNote` as before, unreadable is `MovedWithoutNote` saying the
  note may have been posted. `advance`'s suffix is "if it is missing, add it
  with `tcw work comment`".
- `JiraBackend.set_stage` reads the ids of the newest `NOTE_WINDOW` comments
  before a note is sent, and `_note_found` counts only a matching comment
  whose id was not among them, so an older identical note cannot hide one
  that never arrived. `_after_drop` raises `MovedWithoutNote(uncertain=True)`
  when the comments cannot be read, and `advance` then says the trace "may not
  have been recorded".
- `tcw/store/yaml_source.py` `_no_dup_keys`: an unhashable key raises a
  `ConstructorError` at its mark. `tcw/config.py` `_merge`: two empty mappings
  take the higher layer's origin. `tcw/work/jira/config.py` `_credentials`
  reports every bad key. `tcw/config_cli.py` `_scalar` writes `bytes` as
  `!!binary` and sets as `!!set` flow mappings, members sorted by written
  form; a list of (key, value) tuples, which is how YAML reads `!!omap` and
  `!!pairs`, as `!!pairs`. `render` reads its output back and raises a
  `BackendError` naming the key of any value that does not read back as
  itself.
- `tcw work new`: `open_backend` and `creation_stage` run before
  `read_piped_stdin` when `--project` is absent. With `--project`, `--stage`
  is a `UsageError`, as the other flags it does not take are.
- `run_provision` loads `tcw-config.yaml` first and, when it cannot be
  parsed, prints the error and returns 1 instead of "Nothing to provision".
- `JiraClient._request` adds `Authorization` with `add_unredirected_header`,
  so urllib does not copy it onto a redirected request.
  A 401 whose `HTTPError.geturl()` differs from the requested URL is a
  `TrackerAuthError` naming the address it was redirected to and
  `work.jira.site`, not "rejected the credentials".
- `tcw/validate.py` `_work_target_findings`: in Jira mode, whenever the
  records check does not run (no item, or an item at a terminal stage), the
  item's `capabilities.yaml` is parsed (`_declaration_findings` with
  `folders`), so a single-item check and a viewer save report a malformed
  one whatever the stage, as a full `tcw validate` does.
- `FsCapabilitiesStore.reset` refuses when `_nested_entries` (shared with
  `remove`) finds a `meta.yaml` below the override folder.
- `FsTaxonomyStore.add` refuses a `slug` that is not `is_slug`, after
  `_safe_store_id`, so `../evil` is still "invalid slug".
- `FsStoreProvisioner._run` passes `GIT_TERMINAL_PROMPT=0`,
  `GCM_INTERACTIVE=never` and an empty `GIT_ASKPASS` (git then skips every
  askpass program, including `core.askPass`), removes `SSH_ASKPASS`, and sets
  `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` unless `GIT_SSH_COMMAND`, `GIT_SSH`
