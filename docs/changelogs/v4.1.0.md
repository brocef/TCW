# v4.1.0

## Changed

- The 3.x to 4.0 migration guide says that in a Jira-mode project plain
  `tcw validate`, and the check `tcw migrate` runs after a real run, do not
  check what items' `capabilities.yaml` files declare; the Jira order gains
  a fourth step, `tcw validate --remote`. Its B10 bullet and "Names and
  addresses" section describe the child-prefixed entries. (TCW-119)

- A Jira-mode item's state file holds `ticket: <KEY>` instead of
  `ticket: <work.jira.site>/browse/<KEY>`: `JiraBackend._item_file`, used by
  `tcw work new` and `tcw work tickets adopt`, writes the key alone, so an
  item file no longer carries the Jira site's address. (TCW-177)
- `tcw validate` (`_item_file_problems` in `tcw/work/jira/backend.py`)
  accepts a `ticket` value with no `/` when it equals the folder's key, and
  reports "ticket '<v>' is not the folder's key, <KEY>" otherwise, the value
  quoted so an empty or multi-line one reads on one line; a value that is
  not a string is reported the same way. A value
  with a `/`, the link TCW 4.0.0 wrote, is checked as before: on
  `work.jira.site`, naming the folder's key. (TCW-177)
- The message for a Jira item folder with no state file reads "is missing;
  it holds the ticket's key". (TCW-177)

- `tcw migrate` writes a 3.x Jira item's `ticket: <work.jira.site>/browse/<KEY>`
  as `ticket: <KEY>` when `<KEY>` is the folder's key (`_ticket_key` in
  `tcw/migrate/stores.py`, the site read by `_jira_site` in
  `tcw/migrate/plan.py` from the project's own layers); any other value is
  carried over as before. A 3.x file left beside a 4.0 file holding either
  form is an equal pair, not B11 (`_both`'s `also`). (TCW-177)
- The item file format changes, so this release is 4.1.0, not a patch:
  TCW 4.0.0 refuses a file stamped `tcw-version: 4.1.0` as written by a newer
  TCW. (TCW-177)

## Fixed

- `tcw migrate` (C16) converts an entry under `taxonomy:` in an item's
  `capabilities.yaml` whose first part is a listed child project's ID to
  `<child>.taxonomy/<rest>` (`legacy.route_term_entry_3x`, called from
  `references.Owners.owner_of`), as `route_entry_3x` already did for the
  capability lists. 3.x's reading is kept where it names an `extends` source
  or finds the whole path in the project's own or an inherited taxonomy.
  Where the child's ID is also a first folder of one of those taxonomies,
  the run is refused with B10; the `TermClash` it returns names each project
  that has the folder and offers one full identifier per reading. Before
  this, such entries became `<project>.taxonomy/<child>/<rest>`, which
  `tcw validate` reported as unresolvable in a project keeping no taxonomy.
  (TCW-119)

- **The search for a project no manifest entry places no longer climbs from
  a copy into the main checkout it was made from (TCW-120).** `search_rounds`
  (`tcw/store/project.py`) now leaves out of every climb made from where a
  folder is the main checkout of each linked worktree enclosing that folder
  that is stored inside its own main checkout, and the folders between the
  two that are in the main checkout's repository (same git common folder);
  the folders above that main checkout, and a separate repository between
  the two, are still climbed. New helpers `_under_a_linked_worktree`,
  `_left_out_of_the_climb` and `_climb`. The walk outward goes through every
  enclosing checkout, main or linked, so it is not stopped by a plain clone
  in between, and it starts at the folder searched from, so the active
  worktree's own main checkout is left out too when a separate repository
  lies between the two. It applies to the round read as written, to a
  related project's search made outside the active worktree, and to an
  active project in no worktree, wherever the command runs.
  `_checkout_of` (cached in `_CHECKOUT_CACHE`) is now the one place that
  asks git where a folder's checkout, main checkout and git common folder
  are, reading a submodule's main checkout from `core.worktree`;
  `worktree_anchors` and `_same_place_in_two_checkouts` are built on it, so
  each folder is asked once per process, and a submodule's own linked
  worktree kept inside the submodule's checkout is handled as any other.
  A copy made of nested worktrees at `.claude/worktrees/<name>`, as Claude
  Code makes, no longer fails with "declared by more than one folder:
  …/.claude/worktrees/w and …/MAIN", no longer reports a 3.x main checkout
  as needing `tcw migrate`, and no longer reads the main checkout's project
  when the copy lacks it. `tcw migrate`'s prediction (`search_4`) follows,
  so migrating in such a copy no longer writes a manifest entry the main
  checkout's run does not. Cost: no git process unless a `.git` file lies
  above the folder searched from, or the active worktree's folder is in
  another repository's checkout.

## Internal

- Web development dependencies: `minimatch` now resolves to 11.0.4 everywhere
  (it was 3.1.5 and 9.0.9), through a `pnpm.overrides` entry of `^11.0.1` in
  `package.json`, because ESLint 9 and typescript-eslint 8 ask for older ranges.
  This fixes the denial of service through globparts amplification in versions
  before 11.0.1 (Dependabot alert 89).
- Web development dependencies: `vitest` moves from 4.1.11 to 4.1.12, which
  brings `@vitest/mocker` to 4.1.12. This fixes code injection through
  unauthenticated manual mock registration (Dependabot alert 88) and the Windows
  backslash path traversal that got around the redirect allowlist (Dependabot
  alert 87).

- This repository's item files under `docs/work/` name their tickets by key,
  and are stamped `tcw-version: 4.1.0` as part of the release commit.
  (TCW-177)
