As a user, I bind my own agent skills or shell commands to named lifecycle stages and transitions in `tcw-config.yaml` under `work.lifecycle`, so TCW's fixed contract carries my team's methodology without TCW knowing anything about it.
A binding declares one **kind** explicitly — a bare string is rejected rather than guessed at — and the kind says where its text or command comes from: `blob:` is text I write inline, `file:` is a path in my project, `generate:` is a script of mine that receives the work item as JSON on stdin and prints whatever it likes, `builtin: true` is TCW's own default so I can add to it rather than replace it, `skill:` names an agent skill, and `command:` runs a program.
Bindings also declare **what they are for**. A `pre:` binding is a check that runs and may fail. A `prompt:` binding resolves to instructions my agent reads, and every match is concatenated in the order I wrote them. An entry under `artifacts:`, keyed by lifecycle document name, is a template — there the first match wins, so a `builtin` fallback belongs last.
Any binding may carry `when: {tags, not_tags, type}`, so a bug gets different instructions and a different template than a feature. Three keys, deliberately: anything harder belongs in a `generate:` script, which is real code and can decide anything.
Declaration order is significant. `tcw validate` rejects an unknown id, a malformed shape, a blank or duplicated reference, a kind used in a position that does not allow it — naming `generate:` when I reach for `command:` in a prompt — a `when:` with an unknown key or an impossible value, a `file:` that does not exist or resolves outside my project even through a symlink, and an artifact entry that could never be reached, naming the offender each time.
**Nearly everything I configured before this still works and still prints the same thing** — a stage id with a plain list of skills or commands under it means exactly what it always meant, and prints exactly what it always printed. One thing to change if I have it: an *empty* prompt list — `prompt: []`, or a stage id with nothing but `[]` under it — is now refused by `tcw validate`, which names the stage. An empty list never said anything, and now that a stage I have configured nothing for falls back to TCW's own instructions, an empty list reads as an opt-out that it is not. If I meant "this stage should say nothing", I write `prompt: [{blob: ""}]`; if I meant nothing in particular, I delete the line.
TCW runs my `command:` bindings around transitions: `pre` failures abort the move before anything is written, and `post` failures never roll it back. `skill:` bindings are named for my agent to invoke; the CLI cannot run them.
Hooks run from the project root with `TCW_SLUG`, `TCW_STATUS`, `TCW_TRANSITION`, and `TCW_NODE_ROOT` set, under a configurable timeout. A check carrying a `when:` runs only when it matches, and one that cannot be evaluated does not run.
A `generate:` script additionally gets the work item as the same JSON `tcw work show --json` prints — its request capped so a huge one cannot flood the pipe, with a flag telling the script that happened — plus `TCW_HOOK_ROLE`, `TCW_HOOK_KIND`, `TCW_HOOK_ID`, and `TCW_HOOK_PHASE` so a one-line script needs no JSON parser. Its output is capped and its timeout enforced, and **a script that exits non-zero contributes nothing at all** rather than the half a prompt it printed first. Because resolution can re-run, a generator has to be side-effect-free.
`tcw serve` runs no hooks.
