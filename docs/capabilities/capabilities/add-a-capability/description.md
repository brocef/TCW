As a user, I run `tcw capabilities add <namespace/path> [name]`, with an optional `--status <status>` (default `Missing`) and the capability's body piped on standard input, to create a capability. On success the command prints the new capability's qualified path on standard output and names each file it wrote on standard error. A path already taken is refused (exit 3) and writes nothing, and so is a path my project already inherits a capability at: the message names that capability and says to override it with `tcw capabilities set`, which writes only the fields given, rather than a full copy.

The record's fields are the locked set `tcw capabilities set --field` accepts — `Status`, `Priority`, `Lifecycle`, `Superseded by`, `Subject`, `Feature`, `Roles`, `When`, `Gaps` and `Blocked by`. The 2.x fields `Planning doc` and `Tracker` are retired: a capability links to work the other way, through each work item's `capabilities.yaml`.

Adding a capability writes files and nothing else: it stages and commits nothing, and works the same inside or outside a git repository. A write that fails part-way is rolled back: whatever the command created is removed, and whatever was already there is left as it was.

A capability is a folder holding `tcw-capability.yaml`. `tcw capabilities add --parent` writes `parent:` and, when the parent is one of this project's own capabilities, reads the path inside the parent's folder: with parent `billing/invoices`, `bulk` makes `billing/invoices/bulk`, and a path that already starts with `billing/invoices/` is used as given. `--flat` reads the path as without `--parent`, namespace folder first, and `--flat` without `--parent` is a usage error (exit 2). Under an inherited or another project's parent the path is read as given, and a `not nested:` line says so. The command warns when the folder sits in another capability's folder that the parent does not name. A new capability's state file holds no `id`: its path is its identity.
