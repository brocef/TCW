As a user, after I have overridden an inherited capability with [`tcw capabilities set`](tcw://C/capabilities/override-inherited), I drop that override and re-inherit the original by running `tcw capabilities reset <path>` — no hand-deleting of the override folder. It accepts the id-path, my project's full identifier for the override, or the full identifier of the capability it overrides (`reset core.capabilities/cli/x` means "stop overriding this"); whichever I give, what it removes is my project's own capability at that path. `reset` removes only my override, and each folder above it that the removal leaves empty — each file and folder removed is named on standard error, and nothing is staged or committed — and never touches the project the capability is inherited from. If the path has no override it is refused (exit 3) with a clear message: a capability of mine that overrides nothing tells me to delete it with [`tcw capabilities rm`](tcw://C/capabilities/remove-a-capability) instead, and a path my project has nothing of its own at tells me there is nothing to drop. It is refused (exit 3) while another of my project's own capabilities or terms names the override by its full identifier (in `Superseded by`, `Blocked by`, `Roles`, `When`, `Subject`, `Feature`, `relatesTo`, `vocabulary` or `parent`), since that identifier stops existing once the override is gone: the message names each one and the field, and tells me to repoint it at the overridden capability's full identifier. It is also refused (exit 3) when a capability sits in a folder under the override's, since dropping the override folder would delete it too: the message names each one, and tells me to delete a local one with `tcw capabilities rm` and drop a nested override with `tcw capabilities reset` first. `reset` reverts the whole override at once; to change a single inherited field back I use `set … --field K=<value>` instead.
