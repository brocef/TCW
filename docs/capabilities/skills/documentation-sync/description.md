As a user or agent, I use the `documentation-sync` skill when a change is finished, to decide which of my project's documents it must update. The skill reads the project's documentation entries — each a document, a trigger saying when it must change, and a description of how to write it — from `tcw work docs`, or from a `## Documentation Sync` section in the project's agent guide when the project is not a TCW node or has declared none. It evaluates each trigger against the change and updates only the documents whose trigger fires.
In a TCW project the lifecycle uses it three times: at `plan`, to name a documentation task for every trigger expected to fire; at the end of `implement`, as one pass over the finished change before `outcome.md` is written; and after completion, to offer the choice of a version bump or keeping the current version, and to run the version cut when one is chosen.
Declaring documentation entries in the first place is the `configure` skill.
How it evaluates triggers, plans documentation tasks and offers a version is TCW's default text, which my project can replace or add to under `work.procedures.documentation-sync`; where the entries come from and the lifecycle points above cannot be replaced. Outside a TCW node the skill uses TCW's default.
