As a user or agent, I use the `documentation-sync` skill when a change is finished, to decide which of my project's documents it must update. The skill reads the project's documentation entries — each a document, a trigger saying when it must change, and a description of how to write it — from `tcw work docs`, or from a `## Documentation Sync` section in the project's agent guide when the project is not a TCW node or has declared none. It evaluates each trigger against the change and updates only the documents whose trigger fires.
In a TCW project the lifecycle uses it twice: at `plan`, to name a documentation task for every trigger expected to fire; and at the end of `implement`, as one pass over the finished change before `outcome.md` is written. Nothing in the lifecycle raises a version cut; when I ask for one, the same skill runs it.
In a project that keeps per-version release notes and changelogs, each finished change adds its entries as its own file in an `upcoming/` folder rather than editing a shared file, so work finished on separate branches merges without conflicting there; the version cut combines those files into the version's document, one heading of each kind.
Declaring documentation entries in the first place is the `configure` skill.
How it evaluates triggers, plans documentation tasks and runs a version cut I asked for is TCW's default text, which my project can replace or add to under `work.procedures.documentation-sync`; where the entries come from and the lifecycle points above cannot be replaced. Outside a TCW node the skill uses TCW's default.
