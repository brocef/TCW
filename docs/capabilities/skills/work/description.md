As a user or agent, I open the `work` skill to learn how to drive the `tcw work` command: filing, planning, starting, implementing, verifying and completing work items, resuming one across sessions, splitting an item into child items, and coordinating work across connected projects. The skill carries the judgment on top of the command. It names `tcw` commands and never has me edit the work store by hand where a `tcw` command does the job.

Three procedures in the skill are carried out by the agent rather than by a `tcw` subcommand, because each needs judgment the command-line tool cannot supply. I reach each one by asking the `work` skill for it, and each works the same under Claude and Codex.

**Searching the work items by description.** I describe what I am looking for on the board — what to look for, optionally what to ignore, and optionally how to sort it — and get back the matching work items as a table. Deciding whether an item is _about_ what I asked is judgment a substring match cannot supply.
The search covers the live board by default and reaches closed work when my description asks for it, so "have we done this before" finds the completed item rather than silently missing it. It spans connected projects when I ask about them, and keeps a descendant item's qualified `<project-id>/<slug>` address so every row in the answer is one I can address.
The result carries the same columns the board prints — slug, status, lifecycle stages, priority, title, tags, and the blockers, claimant, and ready-to-close state a board row shows only when it applies — copied from the board rather than recomputed, so the table cannot disagree with `tcw work list`. It tells me how it read my description, and says plainly when nothing matched instead of handing me an empty table. Nothing is changed by searching: no item moves, no field is edited, no file is written.

**Auditing and pruning the backlog.** I ask for an audit of my backlog and get a structured cleanup report. The audit identifies items that look completed, stale, outdated, misplaced, duplicated, blocked without a useful next step, or too vague to implement safely. It also reports dependencies an item states in prose but never recorded, so the board stops showing blocked work as ready to pick up.
The audit does not silently change work items. It reports recommended actions — complete, drop, revise, split, move to another TCW node, or keep as it is — so an agent or user can prune the backlog while keeping each decision reviewable.

**Consolidating external plans into work items.** I ask for planning documents that live outside the TCW work system to be found and converted into work items. Deciding what counts as a plan, and how its content maps onto lifecycle artifacts, needs judgment. When I name no paths, it searches sensible planning locations inside the project while excluding `docs/work/`, so existing work items are not imported a second time.
For each external plan I accept, it creates a backlog item, keeps the source document's useful content as lifecycle artifacts, and reports which old file became which new work item slug. Once the migration succeeds I can have the old documents deleted, so the TCW backlog becomes the lasting planning source. Because that step destroys files, it always confirms with me first — one grouped approval naming every file by path — and it only deletes files git has already committed, so anything it removes I can get back. Untracked or uncommitted sources are reported and left in place.
