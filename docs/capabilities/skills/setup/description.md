As a user or agent, I open the `setup` skill when TCW does not work yet: the `tcw` command-line tool is missing, broken or out of date, a directory does not use TCW, or a TCW project from elsewhere is not working on this machine. It walks first-time setup in order — installing the tool, setting up the project until `tcw validate` passes, then, optionally, a first taxonomy and a first capabilities ledger — and skips any step that is already done. A request to change how a project that already works is configured goes to the `configure` skill instead.

**Starting a taxonomy.** I ask the `setup` skill to start a taxonomy for my project, and the agent studies my codebase in depth, proposes domain terms, refines them with me, and writes the first taxonomy draft.

**Starting a capabilities ledger.** I ask the `setup` skill to start a capabilities ledger, and the agent studies my codebase in depth, proposes user capabilities, refines them with me, and writes the first capabilities draft. When the project has no taxonomy yet, it starts one first, because capabilities point at taxonomy terms.

**Keeping work in Jira.** I ask the `setup` skill to move a working project's items into a Jira project, and the agent walks me through it: choosing the stages and a Jira status for each, writing the configuration, then running `tcw validate --remote`, which reads Jira's workflow and changes nothing. For each finding it explains what TCW needs and helps me change the workflow in Jira's own settings, repeating the check until it reports nothing. TCW never changes Jira's configuration itself.
