As a user or agent, I open the `capabilities` skill to learn how to keep my project's capabilities ledger, the record of what a user can do, through the `tcw capabilities` command. It covers a work item that changes what users can do: checking the change against the capabilities already recorded, declaring the capabilities it adds, changes or removes in the item's `capabilities.yaml` while the spec is written, and linking each capability to a taxonomy Feature.

The records themselves change during implement, in the same change as the code: a new capability is added with the status it really has (`tcw capabilities add <path> "<Name>" --status Supported`), and a changed or removed one is edited or deleted then. The move out of implement checks that every declared record is in place and not `Missing`, so nothing is flipped at completion. On a project with no ledger of its own the declaration can name a child project's ledger, and the skill covers getting the agreed wording for a capability from the project that owns it when several projects share one product.

Capabilities are inherited the same way as taxonomy: through a parent link that passes `capabilities`, listed with `--scope up`, overridden by my project's own capability at the same path, renamed with `tcw capabilities rename` and moved with `tcw capabilities move`. Where several projects give one capability different statuses, `--scope down` or `all` shows each project's status, in `show` and in `--json`. `--parent` names a capability's parent on `add` and `set`. Wording agreed with a parent project is changed in that project, through `tcw -C <folder>` when it is on this machine, or else through that project's own issue tracker.

Starting a ledger from an existing codebase is the `setup` skill, and declaring a parent link is the `configure` skill.
