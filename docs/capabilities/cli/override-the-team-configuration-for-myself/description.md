As a user, I keep my own additions to a project's configuration in files that are mine, so I can shape TCW's instructions to the way I work without changing what my team gets.

**Two personal files.** A user-wide file, `$XDG_CONFIG_HOME/tcw/config.yaml` (or `~/.config/tcw/config.yaml` when `XDG_CONFIG_HOME` is not set), applies to every project I work in. A `.tcw/tcw-config.local.yaml` beside a project's `.tcw/tcw-config.yaml` applies to that project only, and like every file TCW reads in a project's `.tcw/` folder it starts with the version of TCW whose format it follows (`tcw-version: 4.0.0`); a local file without it is refused with the line to add. TCW reads, in order, its own defaults, `.tcw/tcw-config.yaml`, the user-wide file, the local file and then the override variables, `TCW_<KEY>__<PROJECT>`, which may set the same keys (see [Override configuration from the environment](tcw://C/cli/override-configuration-from-the-environment)); a later layer wins. The version is information about the file, not a setting: no layer overrides another's, and the rules below neither need nor refuse it. `tcw init` adds `/tcw-config.local.yaml` to `.tcw/.gitignore`, and `tcw validate` warns when the file is tracked by version control anyway.

**What I may set.** Only what affects me alone: `user.name`, a stage's `prompt` and `post` lists, a procedure's list, and the names of the environment variables holding my Jira credentials. In the project's own `.tcw/tcw-config.local.yaml`, and never in the user-wide file, which applies to every project, I may also list children under `children:`: they are added after the ones the committed file lists, so I can see a child project of my own without changing what the team's file names (see [List a project's children](tcw://C/cli/list-a-projects-children)). Everything else is the team's. A personal file that sets anything else — the project ID, the work store, the backend, a stage's `pre` checks — is a problem naming the file and the key, and every command that reads the configuration stops on it with exit 1. `TCW_NO_PERSONAL_CONFIG=1` makes TCW read neither personal file and no override variable, for a clean run.

**Adding rather than replacing.** A list I set replaces the one below it. An entry `inherit: true` stands for the list the layer below resolved, so `[{blob: "my note"}, {inherit: true}]` puts my note above the team's instructions and keeps them. In `.tcw/tcw-config.yaml`, `inherit: true` stands for TCW's own text, which replaces the `builtin: true` of earlier versions; writing `builtin:` is now an error that names `docs/migration-guide-2.8-to-3.0.0.md`.

**Paths and commands.** A `file:` path is read relative to the folder of the file that declares it, and may not leave that folder; for the two files in a project's `.tcw/` folder that folder is the project root, as though they sat there. A command from any layer runs from the project root, with `TCW_CONFIG_DIR` naming the same folder so my own scripts can find their neighbors.

**I can tell when my files changed something.** `tcw work stage prompt` and `tcw work procedure` add a `note:` line on standard error naming my files when they changed the list being composed, and a failed `post` command names the file it came from. My files apply to the project I am acting in and to each project it inherits configuration from: my settings for a parent, such as the names of my Jira credential variables, reach the project I am acting in through what that parent passes down. A project read for itself, such as the owner of an item named by its full identifier, is read with its team's files and the variables naming it, never with its personal files.

**In a git worktree.** A linked worktree has no personal files of its own until I make them, since they are not tracked. When it has no `.tcw/tcw-config.local.yaml`, the main checkout's is used, as though it sat in the worktree: its `file:` paths and commands run from the worktree. The same holds for the personal manifest, `.tcw/tcw-manifest.local.yaml`.
