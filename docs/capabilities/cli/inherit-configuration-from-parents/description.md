As a user, I let a project take its work settings from the projects it builds on, so a family of projects shares one list of tags and one Jira setup without copying them into every file.

**What crosses a parent link.** A project takes `work.tags`, and every key under `work.jira`, from each parent whose link passes `config` (the default, `inherit: all`, passes it). Nothing else crosses: a parent's stages, procedures, hooks, documentation entries, work path and store locations stay its own. `work.backend` is not inherited either: every project states its own, and one that states none keeps its items in files. A `work.jira` a filesystem-mode project would inherit is ignored.

**How values combine.** The projects are read in the load order (see [Read a project's ancestors in one load order](tcw://C/cli/read-ancestors-in-one-load-order)), farthest first and the project itself last, and the last one that sets a key wins. Mappings merge key by key, so a child that sets only `work.jira.project` keeps its parent's site and credential names. A list or a single value replaces the one before it whole. An `inherit: true` entry in `work.tags` stands for the tags merged before it, so `[{inherit: true}, extra]` adds `extra` to the parents' tags. `null` in a project's shared file removes an inherited value; where TCW has a default for that key, the default applies. A person's own settings for a parent, such as the names of their Jira credential variables, reach the child through what the parent passes.

**A parent that is not here.** A command that needs an inherited value it cannot know, because a project it would come from is not on this machine or its parents could not be read, stops with exit 7 and names the setting and the project. Listing, reading, creating and moving a filesystem project's own items never needs one; applying or listing tags does, and so does every command that opens a Jira-mode store. A setting the project writes itself is always known. `tcw validate` never stops on one: it says, in the missing project's finding, that the configuration inherited from it could not be checked.

**A mistake in a parent.** A problem in a value a parent passes stops only the commands that read that value, with exit 1 and the parent's file named by its whole path; `tcw validate` in the child reports it as a warning, and fails only in the parent.

`tcw work tags add` in a child that has no list of its own writes `inherit: true` first, so it keeps following its parents' tags.
