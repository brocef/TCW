As a user, I run `tcw project config` to see the configuration a command in this project actually runs with: TCW's own defaults, what the project's parents pass down (its tags and Jira settings), the team's `tcw-config.yaml`, my personal files and the override variables, merged. It prints YAML on standard output that reads back as that configuration, and writes nothing. One value is deliberately printed differently: a value under a key ending in `-env` that is not shaped like an environment variable's name is printed as `(value not shown)`, because it is most likely a token pasted where the variable's name belongs. An entry that stands for TCW's own text is printed `- builtin: true` with a comment naming the packaged file it stands for. TCW 3.x's name for it, *tcw config show*, is not a command: typed, it is a usage error (exit 2) whose message names `tcw project config`.

`tcw project config --origin` adds a comment after every value and list entry naming where it came from, in one shape for every layer, so a person or a script can split each label the same way:

- `<project>, <layer> <file>` for a value from a file: the project whose layers it was applied at, the layer (`project` for the team's `.tcw/tcw-config.yaml`, `user` for the user-wide file, `local` for the personal `.tcw/tcw-config.local.yaml`), and the file. A file inside this project is written relative to its root, any other by its whole path. So the team's file reads `# app, project .tcw/tcw-config.yaml`, and a value a parent passes down `# core, project /…/core/.tcw/tcw-config.yaml`. The user-wide file is applied at the active project's layers, so a value it sets carries this project's ID (`# app, user /…/tcw/config.yaml`).
- `<project>, environment <NAME>` for a value from an override variable.
- `built-in` for TCW's own default; for an entry that stands for TCW's own text, the packaged file follows after a comma.

The output ends with a comment line for each value my personal files set that was not used: `# refused:` for a key that belongs to the team, `# skipped:` for a Jira credential name in a project that does not use Jira. In that closing block every value under a key ending in `-env` is shown as `(value not shown)`, in case a token was pasted there by mistake. The same label, without the `# `, is what `tcw project info` shows beside each setting it lists (see [See how a project is assembled](tcw://C/cli/see-how-a-project-is-assembled)).

With a problem in the configuration, plain `tcw project config` stops with exit 1 like every other command. `--origin` still prints everything it could merge, so I can find the line that is stopping the others, then exits 1 with the problems on standard error. A `tcw-config.yaml` that cannot be read leaves it nothing to print.

When an inherited setting cannot be known, because a project it would come from is not on this machine, the command prints nothing, with or without `--origin`, and exits 7 naming the first such setting (`work.tags` before `work.jira`) and the project. When a parent passes a setting with a problem, it prints nothing and exits 1: what it would print is not the configuration commands run with.
