As a user, I choose which projects a list or show command covers with `--scope`, on `tcw work list`, `tcw work show`, `tcw taxonomy list`, `tcw taxonomy show`, `tcw taxonomy search`, `tcw capabilities list`, `tcw capabilities show` and `tcw capabilities search`. `own`, the default, covers my project alone; `up` adds its ancestors, `down` its descendants, breadth first, and `all` both. A sibling, a project that shares a parent with mine, is never covered. For work, `up` adds each ancestor's own items; for taxonomy and capabilities, `up` lists my project's view, its own objects and what it inherits. The projects are taken in scope order: the ancestors, my project, then the descendants.

`--project <id>` keeps only that project's own objects. A project the scope does not cover is refused with exit 2, naming the projects the scope covers.

A covered project that is not on this machine, or cannot be read, is never left out silently: whenever something of it is left out, a line `warning: '<id>' is unavailable, so <what is left out>: <reason>` on standard error names it, with the command that fetches it where there is one, and the command still exits 0. With `--json`, a document that covers more than one project carries `projects`, each covered project with its relation to mine and, for one that could not be read, why.

Under `--scope down` or `all`, a taxonomy or capability list shows each object once, with every override of it in the scope: its record carries `overridden-by`, and `show` prints an `overridden by:` line. An id-path that names nothing of my project's own under the default scope is not found, and the message says to add `--scope up` when my project inherits an object there.
