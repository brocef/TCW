As a user, I run `tcw taxonomy rm <path>` to delete one of my project's own terms, an override of an inherited term included. The path addresses a term inside the taxonomy tree and nothing outside it — one that tries to escape (`../capabilities/…`) matches no term and deletes nothing. The tool refuses (exit 3) to remove a term that belongs to another project (its full identifier, or a path my project has nothing of its own at but inherits a term at), a term with other terms nested under it, and a term another local term still names in `relatesTo` or a feature's `vocabulary`; the refusal names what is in the way and deletes nothing, so `tcw validate` never fails because of a removal that succeeded. References from the capabilities ledger (`Subject`, `Feature`) are not checked here; `tcw validate` reports those. When the term removed was an override, standard error adds `<id-path> now shows <full id>`, naming the inherited term the path shows again; when the inherited terms cannot be read, that line is left out and the removal still happens.

Removing a term deletes its files, and each folder above it that the removal leaves empty, and nothing else: each file and folder removed is named on standard error, nothing is staged or committed, and a term whose files git has never seen is removed like any other.

A removal is refused while anything it would delete holds a state file, or a TCW 3.x `meta.yaml` or `item.yaml`, which names tcw migrate.
